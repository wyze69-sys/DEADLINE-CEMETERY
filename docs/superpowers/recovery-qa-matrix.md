# Adversarial recovery QA matrix

QA checklist, not a verification verdict. Read baseline `server/plan.js`, `server/store.js`, `server/app.js`, `tests/plan.test.js`, `tests/api.test.js`, and recovery design. Implementation is concurrent; source observations below are not findings against the final implementation. No application/test edits or test executions performed.

## Fixture conventions

Freeze planning date at Monday **2026-11-02**. Use stable assignment/task IDs and independent temporary stores. Unless stated otherwise: active, incomplete, unblocked tasks with explicit positive remaining estimates. `E` = original estimate, `R` = remaining estimate, `S` = configured session cap. Availability fixtures specify calendar-day budgets; translate into the API's actual weekday schema. Assertions describe semantics, not speculative response field names.

## Additional high-value regressions

- **Legacy normalization / confirmation honesty:** Incomplete legacy task without E/R defaults E=R30, splittable=false; completed defaults R0. GET does not write migration. Normalization must not convert an assumed/default or extracted estimate into a user-confirmed estimate. `confirmed:true` review of a brief must not silently imply the user independently verified every numerical assumption. If estimate-confirmation provenance is not modeled, readiness copy must say it is conditional on current/default estimates, never guaranteed safe.
- **Submission and reopening:** Log progress, mark submitted with unfinished confirmation, then unsubmit. Plans exclude all submitted work without deleting tasks/history/remaining; unsubmit restores exactly its prior R and blocked state. Completed tasks do not resurrect. Finishing tasks is not submission and must not set submittedAt.
- **Deadline inheritance:** Assignment due Tue; task override Mon. Allocate by Mon. Clear override -> inherit Tue. Clear assignment deadline too -> undated. No stale cached effective deadline; importance never outranks an earlier deadline.
- **Blockers and shared budget:** A blocked R60 due Mon, B unblocked R60 due Mon, Mon60. B gets60; A consumes0 but remains visible and prevents an all-work-safe verdict. Resolve A's blocker and recompute fresh: no capacity double spend or stale exclusion.
- **GET purity / plan reruns:** Compare raw stored data before/after daily and recovery GETs. Repeating the same forecast yields identical allocation order and totals and never decrements remaining or permanently consumes availability. New session or changed weekday settings invalidates stale forecast results.
- **Numeric boundaries / inconsistent payloads:** Check 0, negative, fractional, strings, null, enormous values for remaining/session/reported minutes and availability; exact bounds per documented schema. Continue/blocked require positive R; finished canonicalizes R0. Never round silently, use NaN as available capacity, or accept unknown weekday/query keys that change semantics.
- **No double-counted display totals:** Same task appearing in multiple daily allocations or attention buckets counts once in remaining/due workload, while allocation totals sum session amounts. Across each calendar day sum all assignments' allocations <= that day's known budget. Across the horizon per-task allocation <= initial R. Forecast task inventory totals and daily capacity must reconcile programmatically.

## Baseline seams worth targeting first

- Baseline `plan.js:14-17` schedules/sums `estimatedMinutes`; missing one replacement can yield correct cards with incorrect warning/remaining totals.
- Baseline `app.js:27-30` reconstructs task objects. A new field or session history omitted here can disappear on unrelated PATCH; new defaults can overwrite explicit existing values.
- Baseline `app.js:56-62` changes submitted state before validating metadata; Store currently makes failed actions nonpersistent, but new settings/session code must preserve that isolation.
- Baseline `store.js:13-22` serializes read/action/atomic rename per Store instance. Dedupe checks outside that queued action are race-prone; a pre-write response is not evidence of persistence. Multiple independently constructed Store instances do not share a queue, so scope any concurrency guarantee honestly.
- Existing baseline tests cover legacy planning and basic serialized writes but not recovery allocations, session retries/payload conflicts, failed-validation file equality, or calendar timezone invariance. Final implementation may add these concurrently.

## Parent QA acceptance evidence

Use isolated storage only. For each mutating fixture assert response, GET readback, and fresh Store/restart persistence. For every failed write compare pre/post raw file plus semantic state; for every forecast assert no persistent mutation and reconcile daily/shared/per-task sums. Separate results into PASS/FAIL/NOT RUN. This matrix makes no claim that any upgrade is implemented or passing.
